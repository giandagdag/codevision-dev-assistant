# Redesign after the director review (31 Oct 2026)

Gian showed the demo to his director on 30 Oct 2026. The flow and design were mostly agreed,
with changes below. Every decision here was agreed by Gian in the project chat on 31 Oct 2026.
This file is the source of truth for the specs of Phase 4 onwards. Phases 0 to 3 are not
redesigned; the small changes they need are listed in section 9.

Visual reference: `docs/CodeVision_Developer_Assistant_Demo.html` (rebuilt 31 Oct 2026).
Point a spec at one screen of it; do not ask a session to read the whole file.

## 1. The big changes

| Before | Now |
|---|---|
| Generation levels L0 to L3; the developer finished the code | **The LLM writes 100% of the code.** No levels |
| No testing in the capability | **Testing is built in:** checks, unit tests and an Independent Tester agent |
| Developer downloads starter code, re-uploads finished code | **Workspace:** code is written straight into a folder on the developer's laptop and read back from it |
| Developer completes the code | **Developer refines the requirement**, reviews, runs and may edit the code |
| Path 2 "I'll write it myself" | **Removed.** Self-written code goes through "Review my code" |

The Developer Assistant, request tickets and Admin rules live on the **shared CodeVision server**.
Only the generated code lives on the laptop.

## 2. Entry points (Home)

Three cards:
1. **Build something new** (full journey)
2. **Enhance or fix an existing program** (a fix is an enhancement whose change is "make it work as intended")
3. **Review my code** (code the developer wrote himself)

Understand offers to switch from card 1 to card 2 if the description matches an existing program.

## 3. Journey and screen

- Stepper: **Understand, Discover, Approach, Build & Test, Your review, Handoff**
- Layout unchanged: chat on the left, tabbed side panel on the right
- Tabs: **Summary** (record plus version history v1, v2 with diffs), **Discovery** (plus impact for
  enhancements), **Approach** (file plan, decisions, test plan, 4 gate checks), **Build** (live
  progress, rounds, files written, workspace status), **Tests** (Tester report), **Audit**
- Header chip: workspace folder with connection state and a **Re-scan** button

New statuses after Discover:

| Status | Meaning |
|---|---|
| APPROACH_PROPOSED | Waiting for the developer to confirm approach and test plan |
| READY_TO_BUILD | All 4 gates passed |
| BUILDING, TESTING, TESTER_REVIEW | Build loop running |
| READY_FOR_REVIEW | Green or yellow result, written to the workspace |
| NOT_PASSING | Red: round cap reached |
| REVISION_IN_PROGRESS | A Refine lane is running |
| ESCALATED | With the named senior |
| HANDED_OFF | Locked |

## 4. Memory and context (director question 1)

- Not a chatbot that re-reads the chat. Each LLM call sends: charter slice, **the current request
  record**, the one question, the developer's answer. Chat messages are stored but not re-sent.
  The record is the memory. Prompt size stays flat however long the chat.
- Every turn is saved. "My recent requests" reopens a request at the same step the next day.
- No memory across requests, by design.
- Context window = the **server's configured limit** per model name, not the model's maximum.
  Still to ask the CodeVision team. It matters most in Build (code files are large).

## 5. Phase by phase

### 5.1 Understand (built; small additions in section 9)
- Acceptance criteria must be testable (Given / When / Then style).
- **Revision mode** (Refine lane "requirement"): reopens the same request starting from the last
  confirmed record, asks only about the change, shows a diff, confirm saves **record v2**.
  Same CVDA number. `da_request_records` is already keyed by (request_id, version).
- **Enhancement mode:** "What does it do today?" (AI pre-fills from the code, developer corrects),
  "What should change?", **"What must NOT change?"**, then inputs, outputs, success and failure.
- **Review my code:** a short Understand with 3 to 5 acceptance criteria.
- New CVDA instead of a new version: only after handoff, or for a genuinely different change.
  The new request is linked ("follows CVDA-...").

### 5.2 Discover (Phase 3, in progress)
- Still valid. Results should record which record version they were based on.
- Enhancements: find the program by **name (plain-code catalog search)** or **description
  (code index, top 3)**; the developer always confirms.
- Catalog lookup is plain code: file -> capability -> named senior. Not in the catalog: the
  developer picks a capability and Admin is notified to confirm ("Unassigned" queue).
- **Impact:** who calls the functions being changed. Un-park a light **P16** (find imports and
  calls with the standard-library `ast`).
- **Freshness check** before an enhancement: the browser reads the target files from the
  workspace and compares with Bitbucket `main`. Different: "run git pull first, or confirm your
  local changes are intentional".

### 5.3 Approach (replaces the Readiness Gate)

| Part | Written by | Checked by |
|---|---|---|
| File plan (CodeVision folder layout) | Generator | App: allowed folders, naming, protected files |
| Reuse decisions from Discover | Generator | Developer |
| Key design choices, shown as buttons | Generator | Developer picks |
| **Test plan** in plain language, one or more cases per criterion | **Tester**, in a separate call | **Developer approves** |
| Flag-for-review zones touched | App | Warning, carried to handoff |
| Libraries used | Generator | App: approved list only |

- A1: the developer must approve the test plan. A2: he can add his own cases in plain language.
- A3: more than **5 files** (Admin setting) -> suggest splitting the request.
- A4: he accepts the file plan or explains the change in chat; he does not edit it directly.
- Gate (all 4): request confirmed, Discover done, approach confirmed, test plan accepted ->
  READY_TO_BUILD.

### 5.4 Build + test loop

1. Tester turns the accepted test plan into `unittest` code (built-in library, no install),
   **once per approach version**. Each test is tagged with its criterion ID (AC-1, AC-2...).
2. Generator writes the code, **one file per AI call** (B1).
3. **Layer A** (plain code): syntax (`ast`), allowed imports, Rule Gate, flag-for-review zones,
   protected files.
4. **Layer B** (plain code): run the tests on the server in a sandbox: separate process,
   temporary folder, **60-second time limit** per run (B5, Admin setting). A run that hits the
   limit is stopped, marked "Timed out", names the test that was running, and counts as a failed round.
5. Fail -> plain-language failure report -> generator fixes **only the failing files** -> step 3.
6. Pass -> Independent Tester review (5.5) -> write to the workspace.

Rules:
- **Tests are frozen** (B2). The generator never edits tests, including tests the developer wrote.
- **One shared budget of 3 rounds per build** (B3, C2) covers test failures and Tester Must fix.
  Each rebuild after a Refine gets a fresh budget.
- Written to the workspace at pass, **and at the cap with a red "not passing" label** (B4).
- Tests are written into the workspace with the code, so the developer can run them himself.
- Runs take minutes (Qwen replies in 10 to 20 seconds): the Build tab shows live progress and the
  developer can leave and come back.

### 5.5 Independent Tester

Runs only after Layers A and B pass. Checks (C1):

| # | Check | How |
|---|---|---|
| 1 | Every criterion has a test | Plain code (criterion tags) |
| 2 | Every criterion's tests pass | Plain code (test results) |
| 3 | Files match the file plan | Plain code |
| 4 | Approach decisions followed | AI |
| 5 | Nothing extra built (scope creep) | AI |
| 6 | Judgement rules from the rulebook | AI |
| 7 | Flag-for-review zones touched | Plain code |

- Sees record, approach, test plan, code and test results. Never the generator's chat.
- Every finding cites file and line plus a criterion or rule; the app rejects findings without evidence.
- Result labels (C3), never "Approved": **Ready for your review** (green), **Ready, with warnings**
  (yellow: Should fix open or a flag zone touched), **Not passing** (red: cap reached),
  **Unable to assess** (Tester reply unusable twice).
- Findings: Must fix, Should fix, FYI. Should fix: "Fix it" (bug lane) or "Accept, with reason"
  (audited, shown at handoff). Must fix cannot be accepted away; the only way past is Dispute.
- The report lives **in the app only**, not in the workspace (C4).

### 5.6 Workspace

- Workspace = **the developer's local CodeVision clone** (C5). Files land in the right `src/`
  folders and he can run the app.
- Mechanism: the browser's **File System Access API** (Chrome and Edge 86+, https only; both
  confirmed for CodeVision). The developer clicks "Choose workspace folder", picks the folder in
  the picker (a typed path cannot be used), and clicks Allow. The page then writes and reads files
  there. Scanning happens when he clicks Re-scan, while the page is open.
- Still to check: bank IT policy can disable it (`edge://policy`, look for "FileSystem").
  Fallback: ZIP download plus "upload folder" for re-scan.
- Only files in the file plan plus this request's tests folder are ever written or read (R1).
- No Bitbucket-branch workspace proposal (Gian's decision: let the directors raise it).

### 5.7 Refine and re-scan (Your review)

Re-scan: the browser reads file-plan files and this request's tests folder, compares with the
fingerprints (hashes) from the last write, shows changed files side by side. Files outside the
plan are warned about, not picked up. The developer's edits and new tests go through all three
layers like AI code (R2); his tests are frozen too (R4).

If his edit breaks a test (R3): "Fix my edit" (bug lane), "My edit is right, the requirement was
wrong" (requirement lane), or "I'll fix it myself" (edit and re-scan).

Refine: he types feedback; the AI suggests a lane; he confirms with a button.

| Lane | New record version? | Flow |
|---|---|---|
| Requirement | Yes (v2, v3...) | Understand revision -> approach and test plan updated (new cases need his approval) -> rebuild |
| Approach | No (the approach has its own version number) | Approach updated -> rebuild |
| Bug | No | Tester writes a test that reproduces the bug, he confirms in one click (R6) -> generator fixes |

Protecting his edits (R5):
1. Never overwrite unscanned edits: before writing, compare each file's fingerprint; changed -> stop, "Re-scan first".
2. Rebuilds patch the current file (with his edits); they do not rewrite it.
3. If the generator touches lines he edited, show both versions; he picks per conflict (standard-library `difflib`).
4. Every written version is kept on the server; one-click restore.

### 5.8 Enhance an existing program
Flow as 5.1 enhancement mode plus 5.2. Before any change, **safety-net tests** (E6):
1. The Tester writes tests capturing today's behaviour of the functions in scope (it may see the
   current code for this).
2. They must pass on the **unchanged** code (proves the tests are right).
3. The developer reviews them in plain language.
4. Tests the requirement deliberately changes are marked "expected to change" and linked to the criterion.
5. After the change, every other safety-net test must still pass.
Screens and database-heavy code are hard to cover; anything not covered is listed as
"Not covered by safety net, check manually". The generator gets only the functions in scope, not whole files.

### 5.9 Review my code
Short Understand (3 to 5 criteria) -> pick workspace and files -> Discover -> all three layers
(the Tester writes tests from his criteria) -> he fixes and re-scans, or clicks **"Let AI fix"**
(bug lane, edit-protection rules apply) -> Handoff.

### 5.10 Handoff
- Allowed only when the label is green or yellow (0 Must fix; each Should fix fixed or accepted
  with a reason) **and** a final fingerprint check shows the workspace equals what was last tested.
- The assistant never commits, pushes or approves. The developer commits from his clone and
  opens the PR in Bitbucket.
- PR summary (copy button): request ID, record version, one-line summary; criteria -> tests ->
  results; files changed and which ones the developer edited by hand; reuse and approach
  decisions; accepted risks with reasons; flag-for-review zones (the capability's named senior
  is a required reviewer); safety-net gaps.
- Status HANDED_OFF, request locked.

### 5.11 Escalation
Fixed triggers, checked by plain code (X1):
1. Round cap hit **twice in a row** on the same request (X2, Admin setting)
2. Request or approach out of scope (e.g. the AI is asked to write login code)
3. Developer disputes a Must fix
4. Tester "Unable to assess" twice
5. Developer clicks "Get help"

Senior inbox actions: overrule a finding (audited), send guidance (goes into the chat and the next
AI call), take over, close. Flag-for-review zones are **not** an escalation: they make the senior a
required PR reviewer (X3).
